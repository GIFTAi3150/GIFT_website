# ドメイン切り替えプラン

**目的：** `gift-inc.org` を訪れた人が新しいウェブサイトを見られるようにする。**ダッシュボード・ブログ・API・お問い合わせフォームには一切触れず**、7/8のような事故も繰り返しません。

本ドキュメントでは、プランの内容・安全である理由・想定される技術的な疑問への回答をまとめています。

---

## 1. すでに準備できていること

- **旧ページの転送設定は、すでにコードに実装・公開済み**です：`/about/` → `/company`、`/privacypolicy/` → `/privacy`、`/lstep/`・`/lsteprpa/` → `/services/aiops`。新サイト側の設定として現在の環境ですでに動作しています。
- **お問い合わせフォームはドメインに依存していません。** 送信先は `gift-original.jp`（`gift-inc.org` とは別ドメイン）経由です。コードを直接確認済みで、今回の変更の影響を受けません。
- **同じ方式はすでに実績があります。** `aiops.gift-inc.org` を全く同じやり方（新規追加のみ・既存は変更しない）で用意しており、2026年7月6日から問題なく稼働しています。

---

## 2. プラン ― 3ステップ

| ステップ | 内容 |
|---|---|
| 1 | 新しいアドレス `www.gift-inc.org` を新サイト（Vercel）に向ける。DNSレコードを**追加するだけ**で、既存の `gift-inc.org` レコードは変更しません。 |
| 2 | `www.gift-inc.org` が新サイトを正しく（SSL付きで）表示するか確認する。 |
| 3 | 現在のホスティング側にルールを1つ追加：`gift-inc.org`（トップページ）に来た人を `www.gift-inc.org` へ転送する。 |

`/DashBoard/`・ブログ（`/support997/`）・APIは、この3ステップのどれにも含まれません。今まで通り同じサーバーで変わらず動き続けます。

メインドメインのDNSは一切編集しません。7/8の事故はDNSレコードの変更が原因でしたが、このプランはその種類の変更を完全に避けているため安全です。

---

## 3. 旧ウェブサイトはどうなるか

- **お客様を含め、訪問者が旧トップページにたどり着くことは一切なくなります。** ステップ3が実施された後は、`gift-inc.org` へのアクセスは**例外なく毎回**自動的に新サイトへ転送されます。外部から旧トップページを閲覧する経路はどこにも残りません。「たまに旧サイトが表示される」ようなことは起こらない設計です。
- **旧ファイルは削除せず、転送の裏に隠すだけです。** 同じサーバー上にそのまま残しておく理由はただ1つ、**元に戻す作業を一瞬で済ませるため**です（「7. 元に戻す場合」参照）。これは「訪問者が旧サイトにアクセスできる」という意味では**ありません**。
- **ブログ（SUPPORT 997）とダッシュボードは、意図的に別扱いです。** これらは「取り残された旧サイトの一部」ではなく、現在も現役で、今まで通り公開され続けるべきものです。転送ルールの対象外としているのは「隠している」のではなく、単に対象外にしているだけです。

## 4. よくある質問

**Vercel側はどう扱うのか？**
新サイトはすでにVercel上で稼働しています。`www.gift-inc.org` の追加は、Vercelのプロジェクト設定内での一度きりの作業で、コードの変更や再デプロイは不要です。対応するDNSレコードを追加すると、Vercelが自動的に有効なSSL証明書を発行し（以降も自動更新され）ます。`aiops.gift-inc.org` の時と全く同じ仕組みです。

**現在のホスティング側の転送は、実際にはどう動くのか？**
DNSの変更ではなく、特定のパスに絞った小さなサーバー側のルールです。平たく言うと「トップページ（`/`）へのアクセスがあったら `https://www.gift-inc.org/` へ送る」という設定です。このルールは該当パスにしか反応しないため、`/DashBoard/`・`/support997/`・APIへのアクセスはこのルールに一致せず、これまで通り処理されます。このステップではドメインのDNSは何も変わらず、トップページへのアクセスの扱い方だけが変わります。

**何か壊れる可能性はあるか？**
現実的なリスクを一つずつ確認すると：
- **旧内部ページ**（`/lstep/`・`/about/` 等）— それぞれに対応する転送ルールを追加することでカバー済み（マッピングは作成・確認済み）。
- **メール** — 影響なし。今回の変更はトップページへのアクセスの扱いのみを変えるもので、メール（MXレコード）には一切触れません。
- **証明書** — 現在のホスティングは引き続き自身の有効な証明書でトップページの最初のアクセスを受け、`www` 側はVercelが自身の有効な証明書を発行します。7/8で起きた問題（`www` をカバーしていない証明書）は、Vercelの証明書が `www` を直接カバーするため再発しません。
- **旧ページの深い階層を直接指しているもの**（印刷物・保存済みリンク等）— 一度確認しておく価値はありますが、この転送設定そのものとは別の話であり、実施のブロッカーにはなりません。

**長期的に問題なく機能し続けるか、それとも一時しのぎか？**
一時しのぎではなく、標準的で恒久的な方式です。多くの企業が「ドメイン直打ち → www へ転送」を恒久的に運用しています。メンテナンスが不要な理由は2つ：Vercel側の証明書は永続的に自動更新される、そして転送ルールはそのまま存在し続ける限り期限なく動作し続けます。唯一の見た目上の影響は、転送後にアドレスバーが `www.` 表示になる点です。将来的に「転送なしで `gift-inc.org` そのものを新サイトにしたい」となった場合は、より大きな別プロジェクト（ダッシュボードを先に別アドレスへ移し、その後メインドメイン自体を新サイトに向ける）が必要になりますが、それは将来いつでも選べる選択肢として残しておき、今回のプランの安定運用には影響しません。

## 5. ステップ3の前に確認したい項目

- 新サイトのアドレスとして `www.gift-inc.org` を使う方針でよいか。*（推奨）*
- 転送はトップページのみか、旧内部ページも含めるか。*（推奨：内部ページも含める。すでに準備済み）*
- `/lstep/`・`/lsteprpa/` の転送先は `/services/aiops`*（推奨・準備済み）*か、トップページか。
- **名刺のQRコード ― 確認済み：** トップページを開く仕様であることを確認済み。これはまさに転送されるパスのため、**刷り直しは不要**です。

---

## 6. 2026-07-10 の進め方

1. 本プランを共有し、上記の確認項目への回答を得る。
2. 回答が揃い次第 → ステップ1（`www` のDNSレコードを追加）。この時点では見た目の変化なし。
3. ステップ2を確認（新アドレスが正しく表示され、SSLが有効で、既存の転送も正しく動くか）。
4. ステップ3を実施（トップページの転送ルールを追加）。この瞬間から訪問者に見える変化が発生する。
5. 実施後30〜60分ほど、ダッシュボード・ブログ・お問い合わせフォームを確認する（影響はないはずだが、念のため確認）。

---

## 7. 元に戻す場合

ステップ3の転送ルールを削除するだけで、トップページは瞬時に元の状態に戻ります。旧ファイルを削除していないからこそ、これが可能です。（ステップ1のDNSレコードはそのまま残しておいても問題ありません。）

## 9. リダイレクトルールを正しく書くための実装・検証チェックリスト

今回の作業の中で、書き方を間違えると実際に問題が起こりうる唯一の箇所です。ここは正確に。

**絶対に避けるべき一番の失敗：** ドメイン全体に一致する「キャッチオール（包括）」ルール（例：`gift-inc.org/*` に一致するものすべてを転送）。これをやってしまうと `/DashBoard/`・`/support997/`・APIまで巻き込まれます。ここでのルールは必ず**完全一致（特定パスのみ）**にしてください。ワイルドカードは使わないこと。

**ホスティングがApache + `.htaccess` の場合**（この種のWordPressレンタルサーバー構成では標準的で、今回もこのケースの可能性が高い）：

```apache
# GIFT トップページ転送 — 「# BEGIN WordPress」ブロックより上に配置すること
RewriteEngine On
RewriteCond %{REQUEST_URI} ^/$
RewriteRule ^$ https://www.gift-inc.org/ [R=301,L]
```

内部ページの転送も承認された場合は、パスごとに完全一致の行を追加してください（ワイルドカードは使わない）：

```apache
RewriteRule ^about/?$ https://www.gift-inc.org/company [R=301,L]
RewriteRule ^privacypolicy/?$ https://www.gift-inc.org/privacy [R=301,L]
RewriteRule ^lstep/?$ https://www.gift-inc.org/services/aiops [R=301,L]
RewriteRule ^lsteprpa/?$ https://www.gift-inc.org/services/aiops [R=301,L]
```

これらの行は `.htaccess` 内の `# BEGIN WordPress ... # END WordPress` ブロックより**必ず上**に置いてください。先に評価され、`[L]` フラグにより、WordPress自身のルーティングが処理する前に終了します。

**WordPressのリダイレクトプラグイン（例："Redirection"）を使う場合：** 一致方式を**「完全一致（Exact match）」**にしてください。「前方一致」や正規表現のワイルドカードは使わないこと。パスごとに1エントリーです。

**検証チェックリスト（ステップ3の実施直前・直後に必ず実行）：**

| 確認項目 | 期待される結果 |
|---|---|
| `gift-inc.org/` | `https://www.gift-inc.org/` へ301/308転送される |
| `gift-inc.org/DashBoard/` | 200 — 通常通り表示、**転送されない** |
| `gift-inc.org/support997/` | 200 — 通常通り表示、**転送されない** |
| 使用中のAPIエンドポイント | 通常通り応答、**転送されない** |
| `www.gift-inc.org/` | 200 — 新サイトが表示、SSLの鍵マークが有効 |

一番早い確認方法：`curl -I <url>` でヘッダーだけを確認できます（トップページは `301`／`308` ＋ `Location:` ヘッダー、それ以外は通常の `200` になっているか確認）。ブラウザ不要で、5項目すべて1分以内に確認できます。

**もし「200のはず」の項目が転送されてしまっていたら** → 直ちに停止してください。ルールが広すぎたということです。すぐに修正または削除を。これはまさに「7. 元に戻す場合」がカバーしている状況です。
